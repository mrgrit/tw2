# W13 — 지시를 따르는 모델, 그리고 심판

> **한 줄 요약** — 355M 모델을 **지시 튜닝**한다. 튜닝 전 손실 3.8 이 2에폭 후 1 미만으로
> 떨어지고, 모델이 `### Response:` 뒤에 진짜 응답을 쓰기 시작한다. 그런데 곧 **평가 문제**를
> 만난다 — 자유 형식 응답을 어떻게 채점할 것인가? 답은 **LLM-as-judge**. 로컬 Ollama 모델을
> 심판으로 세운다. **그런데 그 심판이 얼마나 믿을 만한지도 여러분이 검증해야 한다.**
> 마지막으로 **LoRA** 로 "곁가지만 훈련하기"를 배운다.

---

## 학습 목표

1. 학생은 지시 튜닝 전후의 손실·응답 형식 변화를 관찰하고 해석할 수 있다.
2. 학생은 테스트셋 응답을 일괄 생성하고 빈 응답 0건을 확인할 수 있다.
3. 학생은 로컬 LLM 을 심판으로 세우고 **컨테이너에서 호스트 Ollama 로 접속**하는 법을 안다.
4. 학생은 심판의 **상한·하한·결정성**을 스스로 검증할 수 있다.
5. 학생은 `temperature=0` 이어도 저지 점수가 흔들린다는 것을 실측으로 확인하고 해석할 수 있다.
6. 학생은 LoRA 를 구현하고 **B=0 초기화가 항등 게이트**임을 증명할 수 있다.
7. 학생은 LoRA 와 풀 튜닝을 파라미터·메모리·시간·품질 4축으로 비교할 수 있다.

## 0.4 이번 주 배경 지식 — 처음이라면

### 손실 함수가 안 바뀐다는 것의 의미

9주차 사전훈련도, 이번 주 지시 튜닝도 **똑같이 "다음 토큰 맞히기"** 입니다.
코드로 보면 같은 줄입니다.

```python
loss = torch.nn.functional.cross_entropy(logits.flatten(0,1), targets.flatten())
```

**그럼 무엇이 다른가 — 무엇을 맞히게 하느냐가 다릅니다.**

| | 입력 | 맞혀야 할 다음 토큰 |
|---|---|---|
| 사전훈련 | 소설 아무 데나 | 소설의 다음 단어 |
| **지시 튜닝** | `### Instruction:\n45km를 m로\n\n### Response:\n` | **응답의 다음 단어** |

같은 훈련 루프에 **다른 데이터**를 넣으면 다른 행동이 나옵니다. 이것이 12~13주차가
"데이터가 절반이다"라고 말하는 이유입니다.

> 📌 **이 사실이 이 수업의 마지막 개념적 도약입니다.** 모델을 바꾸지 않고 데이터만 바꿔
> 행동을 바꾼다 — ChatGPT 가 만들어지는 방식이 정확히 이것입니다.

### LoRA 란 무엇인가 — 큰 행렬을 두 개의 얇은 행렬로

파인튜닝은 원래 **모든 가중치 행렬을 조금씩 고치는** 일입니다. 355M 모델이면 4억 개를
전부 고칩니다. 옵티마이저 상태까지 합치면 메모리가 8GB 넘게 듭니다.

**LoRA 의 아이디어:** 원래 행렬 `W` 는 **얼려 두고**, 옆에 **얇은 곁가지**를 달아 그것만
훈련합니다.

```
원래:      출력 = W · x                    (W 는 768×768 = 589,824개)
LoRA:      출력 = W · x + (B · A) · x      (W 는 동결. A, B 만 훈련)

A: 768 × r        r=8 이면 6,144개
B: r × 768                6,144개
                          ─────────
                          12,288개  ← 589,824개 대신 이것만 훈련
```

**왜 이게 되는가.** 파인튜닝으로 생기는 변화량은 **큰 행렬 전체를 흔들 만큼 복잡하지 않다**는
관찰이 있습니다. 변화의 "방향"이 몇 개 안 되므로, 얇은 두 행렬의 곱으로 표현할 수 있습니다.
`r` 이 그 방향의 개수입니다.

| r | 훈련 파라미터 비율 | 성격 |
|---|---|---|
| 8 | **0.97%** | 가볍다. 대부분 충분 |
| 16 | 1.94% | 표현력 조금 더 |
| 큰 값 | 늘어남 | 풀 튜닝에 가까워짐 |

> 💡 **메모리가 왜 줄어드는가 — 9주차 계산의 응용입니다.** AdamW 는 **훈련하는 파라미터마다**
> 상태 2개를 듭니다. 훈련 대상이 1%면 옵티마이저 상태도 1%만 생깁니다.
> 실측: 풀 튜닝 **8.28GB** → LoRA r=8 **4.52GB** (45% 감소).

### `B = 0` 초기화 — 항등 게이트

LoRA 를 붙이는 순간 모델이 망가지면 안 됩니다. 그래서 **`B` 를 0으로 초기화**합니다.

```
B = 0  →  B · A = 0  →  출력 = W·x + 0 = W·x     ← 원본과 완전히 동일
```

**적용 직후에는 아무 일도 안 일어납니다.** 그리고 훈련이 시작되면 `B` 가 0에서 벗어나며
조금씩 영향을 주기 시작합니다.

> 📌 **이것이 "시작점 검증"의 전형입니다.** 새 장치를 붙였을 때 **붙이기 전과 완전히 같은지**
> 먼저 확인하고, 그다음 변화를 봅니다. 10주차 가중치 이식 품질 게이트, 14주차 KV 캐시
> 동일성 게이트와 같은 사상입니다. **차이를 측정하려면 먼저 '차이 없음'을 확인해야 합니다.**

### LLM-as-judge — 심판을 세우되 심판도 검증한다

자유 형식 응답은 정답이 하나가 아닙니다. 그래서 **다른 LLM 에게 채점을 맡깁니다.**

```
저지에게 주는 것:  지시 + 정답 예시 + 우리 모델의 응답
저지가 내는 것:    0~100 점
```

**편리하지만 위험합니다.** 심판이 틀릴 수 있기 때문입니다. 이번 주는 저지 자체를 검증합니다.

| 검사 | 방법 | 기대 |
|---|---|---|
| **상한** | 정답을 그대로 넣어 채점 | 100 에 가까워야 |
| **하한** | 엉터리 문장을 넣어 채점 | 0 에 가까워야 |
| **재현성** | `temperature=0` 으로 같은 입력 반복 | 같은 점수여야 |

> 🔴 **실측 결과 셋 다 완벽하지 않았습니다.** `temperature=0` 인데도 점수가 흔들리고,
> 분류 문제 정답에 95점을 준 사례가 있었습니다. 그리고 저지는 연속적인 점수를 주지 않고
> **25점 단위로 뭉칩니다**(앵커링).
>
> **그래서 저지 점수 차이 1~2점은 의미가 없습니다.** 이번 주 표에서 60.87 vs 62.14 를 보고
> "LoRA 가 더 좋다"고 결론 내리면 안 되는 이유입니다.

- `temperature: 0` — 결정적 출력을 의도
- `seed: 123` — 난수 고정
- `num_ctx: 2048` — 프롬프트가 잘리지 않게 충분히

**저지 모델:** `llama3.1:8b` (교재는 모델명을 플레이스홀더로 두었지만, **어떤 모델을 쓰느냐가

### 3.3 실측 결과

| 항목 | 값 |
|---|---|
| 채점 성공 | **110 / 110** |
| 파싱 실패 | **0** |
| 평균 | **60.92점** |
| 표준편차 | 29.34 |

> ⚠️ **교재는 "50점 안팎"을 예상했지만 실측은 60.92 입니다.** 교재가 저지 모델명을
> 플레이스홀더로 두었기 때문에 **예상값 자체가 성립할 수 없습니다.** 저지가 바뀌면 점수가
> 바뀝니다. **평가 지표를 제시할 때는 반드시 "어떤 심판으로"를 함께 적어야 합니다.**

### 3.4 🔴 심판을 검증하라 — V13-1

**심판의 점수를 믿기 전에, 심판이 믿을 만한지 확인합니다.**

| 검증 | 방법 | 실측 |
|---|---|---|
| **상한** | 정답 자체를 채점 → 90점 이상이어야 | ✅ 통과 |
| **하한** | 엉터리 문장을 채점 → 낮아야 | ⚠️ **부분 실패** |
| **결정성** | 같은 (항목, 응답) 3회 채점 → 동일 점수 | ⚠️ **부분 실패** |

**하한 검증의 발견:** `"The weather is nice today."` 라는 완전히 무관한 문장이 소수·합성수
분류 문제에서 **95점**을 받았습니다. 저지도 실수합니다.

**결정성 검증의 발견:** `temperature=0` 인데도 110개 재채점에서 **9건(8.2%)** 이 달라졌습니다.

```
평균 변동폭: 31점 (최대 83점)
그런데 전체 평균은 60.92 → 61.13 (0.21점만 이동)
```

> 📌 **개별 점수는 흔들리지만 평균은 안정적입니다.** 이것이 이 발견의 핵심입니다.
> **"이 응답은 75점"** 이라고 말하면 안 되고, **"이 모델의 평균은 61점"** 이라고 말해야 합니다.
>
> 원인은 서버 측 실행 경로(배치 구성, KV 캐시 상태 등)로 추정되며, **클라이언트에서
> seed/temperature 로 제거할 수 없습니다.**

### 3.5 점수 앵커링 — 저지의 또 다른 특성

110개 점수 중 **61.8%** 가 `{0, 50, 75, 95, 100}` 다섯 값에 몰렸고, 전체 110건에서 서로 다른
값은 **15개**뿐이었습니다.

**이것이 25점 단위 점프의 원인입니다.** 저지는 연속적인 점수를 주지 않고 몇 개의 "앵커"에
붙습니다. 경계선상의 응답은 실행마다 인접 앵커로 튑니다.

## 4. 미션 4 — LoRA: 곁가지만 훈련하기

### 4.1 아이디어

```mermaid
graph TD
    X["입력 x"] --> W["원본 Linear<br/>W (동결)"]
    X --> A["A: in × r<br/>kaiming 초기화"]
    A --> B["B: r × out<br/>zeros 초기화"]
    W --> S["+"]
    B --> M["× alpha"]
    M --> S
    S --> Y["출력"]
    style W fill:#1f6feb,color:#fff
    style B fill:#3fb950,color:#fff
```

**원본 가중치는 얼리고, `A @ B` 라는 저차원 곁가지만 훈련합니다.**
`768 × 768 = 589,824` 대신 `768 × 16 + 16 × 768 = 24,576` 만 학습합니다.

### 4.2 B=0 초기화가 왜 결정적인가

```python
self.A = nn.Parameter(torch.empty(in_dim, rank))
nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))
self.B = nn.Parameter(torch.zeros(rank, out_dim))   # ← 0!
```

`B = 0` 이므로 `x @ A @ B = 0` 입니다. 따라서 **LoRA 를 붙인 직후의 출력은 원본과 완전히
같습니다.**

> 📌 **이것이 "항등 게이트"입니다.** 훈련을 시작하기 전 모델이 망가지지 않았음을 보장합니다.
> **LoRA 적용 직후 val 손실이 원본과 일치하는지 확인하는 것**이 이 미션의 게이트입니다
> (실측 3.8172 — 튜닝 전 손실과 동일).

### 4.3 스케일은 α 인가 α/r 인가

원 논문은 `α/r` 스케일을 씁니다. 이 교재의 구현은 **`α`** 를 씁니다.

> ⚠️ `r = α = 16` 이면 두 방식이 **16배** 차이납니다. **어느 쪽이든 상관없지만
> 일관되게 쓰고 명시해야 합니다.** 이 실습은 `α` 기준입니다.

### 4.4 실측 비교

| 방식 | 훈련 가능 파라미터 | 비율 | 시간 | peak 메모리 | val 손실 | 저지 평균 |
|---|---|---|---|---|---|---|
| **풀 튜닝** | 406,286,336 | 100% | **98초** | **8.28 GB** | **0.613** | **60.93** |
| **LoRA r=16** | 7,898,384 | **1.94%** | **40초** | **4.58 GB** | 0.649 | **60.87** |
| **LoRA r=8** | 3,949,192 | **0.97%** | **39초** | **4.52 GB** | 0.658 | **62.14** |

**LoRA r=8 은 파라미터의 0.97% 만 훈련하고 메모리를 45% 줄이면서 저지 평균은 오히려 높습니다.**

> 💡 **단, 저지 평균 차이(60.87 vs 62.14 vs 60.93)는 3.4절에서 본 측정 오차 범위 안입니다.**
> "LoRA 가 더 좋다"고 결론 내리면 안 됩니다. 맞는 결론은 **"품질 저하 없이 비용을 크게
> 줄였다"** 입니다.

## 5. 에이전트에게 시키는 법 — 이번 주 실전

### 5.1 "측정 오차를 먼저 재라"는 지시

이번 주는 세 가지를 비교합니다(풀 튜닝 / LoRA r=16 / LoRA r=8). 그런데 **비교하기 전에
할 일이 있습니다.**

```text
[할 일] 저지 설정을 그대로 두고 같은 응답 집합을 3회 채점해, 점수의 표준편차를 구할 것
```

**이것이 "이 실험에서 몇 점 차이가 의미 있는가"의 기준선입니다.** 측정 오차가 ±2점인데
두 방법이 1.3점 차이라면, 그건 **차이가 없다는 뜻**입니다.

> 📌 **11주차 ±1%p 재현 게이트의 일반화입니다.** 그때는 "같은 설정에서 같은 값이 나오는가"를
> 물었고, 이번엔 "같은 설정에서 얼마나 흔들리는가"를 **숫자로 잰 뒤** 비교합니다.
> 14주차에서 "우리 방법이 낫다"고 주장하려면 이 절차가 필요합니다.

### 5.2 컨테이너에서 호스트 Ollama 로 — 네트워크 함정

저지 모델은 **호스트**의 Ollama 에서 돕니다. 그런데 컨테이너 안의 `localhost` 는
**컨테이너 자신**입니다.

```python
# ❌ 컨테이너 안에서 이렇게 쓰면 연결 실패
base_url = "http://localhost:11434/v1"

# ✅ 컨테이너에서 호스트를 가리키는 주소
base_url = "http://172.17.0.1:11434/v1"       # docker0 브리지 게이트웨이
```

**에이전트는 이 함정에 잘 빠집니다.** 예제 코드가 대부분 `localhost` 로 되어 있기 때문입니다.
프롬프트에 명시하십시오.

```text
      게이트웨이 주소를 쓸 것. 연결 확인을 먼저 하고 진행하라.
```

### 5.3 이번 주에 에이전트가 실제로 하는 실수 세 가지

| 증상 | 어떻게 알아채나 | 대응 |
|---|---|---|
| **`localhost` 로 저지 호출** | connection refused | 브리지 주소 사용. `curl` 로 먼저 확인 |

두 번째는 조용히 틀립니다. LoRA 를 붙여도 원래 가중치를 얼리지 않으면 **풀 튜닝과 똑같이**
동작합니다. 시간도 메모리도 안 줄어드는데, 숫자를 안 보면 모릅니다.

### 5.4 판정 명령 — 게이트 세 개

```bash
docker exec -it llm-lab bash
cd /work/week13

# 게이트 ①: 저지 연결
curl -s http://172.17.0.1:11434/api/tags | head -c 100 && echo "  ← 저지 연결 OK"

# 게이트 ②: LoRA 항등성 — 붙인 직후 원본과 완전히 같은가
python3 -c "
import torch
from lora import apply_lora
from load_and_modify import build_355m
m = build_355m(); m.eval()
x = torch.randint(0, 50257, (1, 16))
before = m(x)
apply_lora(m, r=8, alpha=16)
after = m(x)
print('항등 게이트', torch.allclose(before, after, atol=1e-6))   # True 여야 한다
tr = sum(p.numel() for p in m.parameters() if p.requires_grad)
tot = sum(p.numel() for p in m.parameters())
print('훈련 가능', f'{tr:,}', f'({tr/tot*100:.2f}%)')            # 0.97% 근처
"

# 게이트 ③: 3축 비교표가 갖춰졌는가
cat lora_compare.md          # 시간 / peak 메모리 / val 손실 / 저지 평균
```

> 0이 아니거나 적용 위치가 틀린 것입니다. 이 상태로 훈련하면 결과가 나와도 해석할 수 없습니다.

## 실습 안내

이번 주 실습(`lab_week13.yaml`, 7단계)은 llm-lab 컨테이너 + GPU + 호스트 Ollama 를 씁니다.

### 1) 이 실습을 왜 하는가?

**한 학기의 종착점입니다.** 무작위 초기화 모델에서 시작해 지시를 따르는 모델까지 왔습니다.
그리고 마지막으로 배우는 것은 **"평가를 어떻게 신뢰할 것인가"** 입니다 — 이것이 실무에서
가장 어려운 문제입니다.

### 2) 무엇을 알 수 있는가?

- 구조를 바꾸지 않고 **가중치만으로** 행동이 바뀐다는 것.
- LLM 심판도 **틀린다**는 것, 그리고 그것을 **검증하는 법**.
- `temperature=0` 이 결정성을 보장하지 **않는다**는 것 — 그러나 **평균은 안정적**이라는 것.
- 파라미터의 **1%** 만 훈련해도 품질이 유지된다는 것.

### 3) 결과 해석 (정상 vs 비정상)

| 확인 | 정상 | 비정상 → 의심할 곳 |
|------|------|-------------------|
| 튜닝 전 손실 | **3.8 안팎** | 6점대면 사전훈련 가중치 미로드 |
| 튜닝 후 손실 | train **0.31** / val **0.61** | 1 이상이면 에폭·lr 확인 |
| 응답 수 | **110**, 빈 응답 **0** | 빈 응답이 있으면 EOS 처리 확인 |
| Ollama 접속 | `172.17.0.1:11434` | `localhost` 는 **연결 거부** |
| 파싱 실패 | **0** | 많으면 "정수만" 지시 확인 |
| 저지 평균 | **60.92** (llama3.1:8b) | 저지가 다르면 값이 다름 |
| 저지 상한 | 정답 채점 **90점 이상** | 낮으면 저지 프롬프트 문제 |
| 저지 결정성 | **완전하지 않음** (8.2% 변동) | 완전히 같으면 운이 좋은 것 |
| LoRA B 초기값 | **전부 0** | 아니면 항등 게이트 실패 |
| LoRA 적용 직후 손실 | 원본과 **일치** (3.8172) | 다르면 B≠0 |
| LoRA 훈련 파라미터 | r=16 **1.94%** / r=8 **0.97%** | 100%면 동결 실패 |

### 4) 실전 활용

LoRA 는 오늘날 오픈 모델 파인튜닝의 **표준**입니다. 그리고 LLM-as-judge 는 챗봇·요약·번역 등
자유 형식 출력을 평가하는 사실상 유일한 실용적 방법입니다 — **다만 심판을 검증하는 절차
없이 쓰면 안 됩니다.** 이번 주가 그 절차를 가르칩니다.
