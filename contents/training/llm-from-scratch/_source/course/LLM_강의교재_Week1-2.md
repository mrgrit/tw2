> 본 교재는 『밑바닥부터 만들면서 배우는 LLM』(길벗)과 공식 저장소 `rickiepark/llm-from-scratch`를 기반으로 하며, 모든 실습은 **학생이 직접 코드를 타이핑하지 않고 코딩 에이전트(Claude Code)에 프롬프트로 지시**하여 수행합니다.

# 0장. 이 교재를 사용하는 법

## 0.1 이 수업의 세 가지 규칙

1. **코드를 직접 치지 않는다.** 모든 코드 작성·수정·실행은 에이전트에게 프롬프트로 지시한다.
   - 예외: SSH 접속, `claude` 실행, `/`로 시작하는 슬래시 명령, 파일을 "읽기 위한" 열람은 직접 해도 된다. 금지되는 것은 "코드와 설정을 직접 타이핑·편집하는 행위"다.
2. **에이전트의 산출물을 반드시 읽는다.** 이해하지 못한 코드는 제출해도 점수가 없다. 학기 중 2회 랜덤 구술에서 자기 저장소의 코드를 설명해야 한다.
3. **모든 결과는 증거와 함께.** "됐습니다"는 결과가 아니다. 확인 명령의 출력이 결과다.

## 0.2 제출물 3종 세트 (매주 공통)

| 파일 | 내용 |
|---|---|
| `prompts.md` | 이번 주 에이전트와의 대화 전체 (Claude Code에서 `/export`로 저장) |
| 산출물 | 코드, 그래프, 로그 등 에이전트가 만든 결과물 |
| `report.md` | 검증 노트 1쪽: 한 일 요약 / 검증 내역 / 핵심 개념 / **결과 해석(반드시 본인이 직접 작성)** |

`report.md`의 해석 섹션을 에이전트로 작성하면 표절로 처리한다. 이 수업에서 에이전트는 "손"이고, 해석은 여러분의 "머리"가 하는 일이다.

## 0.3 Claude Code 기초 조작

| 조작 | 설명 |
|---|---|
| `claude` | 터미널에서 에이전트 세션 시작 |
| `/init` | 프로젝트를 스캔해 `CLAUDE.md`(프로젝트 규칙 파일) 초안 생성 |
| `/export` | 현재 대화를 파일로 내보내기 → `prompts.md` 제출에 사용 |
| `/clear` | 대화 기록 초기화 — 새 미션을 시작할 때 사용 |
| `/permissions` | 도구 실행 권한 설정 확인 |
| `Esc` | 진행 중인 작업 중단 |

에이전트는 파일 수정이나 명령 실행 전에 **승인을 요청**한다. 승인 창이 뜨면 반드시 "무엇을 실행하려는지" 읽고 허용하라. 아무 생각 없이 전부 허용하는 습관은 이 수업에서 감점 요인이자, 보안 관점에서 위험한 습관이다.

`CLAUDE.md`는 에이전트가 세션마다 자동으로 읽는 프로젝트 규칙 파일이다. 여기에 넣은 규칙은 매번 프롬프트에 쓰지 않아도 적용된다. 1주차에서 수업 표준 규칙을 이 파일에 넣는다.

## 0.4 프롬프트 작성 5원칙 (이 수업의 핵심 기술)

1. **결과물로 말하라** — "~를 해줘"가 아니라 "~라는 산출물을 만들어줘"
2. **맥락을 줘라** — 작업 디렉토리, 환경(컨테이너 안/밖), 참조할 파일 경로
3. **제약을 걸어라** — 하지 말아야 할 것, 건드리면 안 되는 것
4. **증거를 요구하라** — "완료 후 확인 명령의 출력을 첨부하라"
5. **위험한 작업엔 게이트를 세워라** — "실행 전 계획을 보여주고 내 승인을 받아라"

**나쁜 프롬프트와 좋은 프롬프트 비교:**

```text
[나쁨] 방화벽 설정해줘
```

```text
[좋음]
[목표] UFW 방화벽을 활성화하되 SSH(22)만 허용하고 나머지 인바운드는 차단
[제약] 나는 지금 SSH로 원격 접속 중이다. 접속이 끊기지 않도록
      SSH 허용 규칙을 먼저 추가한 뒤에 방화벽을 활성화할 것
[검증] 완료 후 ufw status verbose 출력을 첨부할 것
[산출물] 실행한 명령 목록과 각 출력
```

나쁜 프롬프트가 위험한 이유: 에이전트가 SSH 허용 없이 방화벽을 켜면 **여러분은 자기 장비에서 쫓겨난다.** 목표·제약·검증이 빠진 지시는 도박이다.

## 0.5 교재 표기 규칙

- **📋 실행 프롬프트 P주차-번호** — 그대로 복사해 Claude Code에 붙여넣는 프롬프트. `<이렇게>` 표시된 부분만 자신의 값으로 치환한다.
- **✅ 검증 프롬프트 V주차-번호** — 실행 결과가 올바른지 확인시키는 프롬프트. 실행 프롬프트와 짝으로 사용한다.
- **⚠️ 경고 박스** — 장비를 잠그거나 데이터를 잃을 수 있는 지점.
- **예상 결과 / 통과 기준** — 이 값이 나오지 않으면 다음 단계로 넘어가지 말 것.

## 1.1 배경: 왜 이 장비는 "특수"한가

여러분 책상 위의 DGX Spark는 일반 PC와 세 가지가 다르다.

1. **CPU가 ARM(aarch64)이다.** 인터넷의 설치 가이드 대부분은 x86 기준이라 그대로 따라 하면 실패하는 경우가 있다. 파이썬 패키지 중 일부는 aarch64용 빌드가 없어서 별도 경로로 설치해야 한다.
2. **GPU가 Blackwell 세대(CUDA 13)다.** 오래된 PyTorch 버전은 이 GPU를 인식하지 못한다. 그래서 우리는 NVIDIA가 배포하는 컨테이너를 기반으로 만든 **골든 이미지** 안에서 실습한다.
3. **CPU와 GPU가 128GB 메모리를 공유한다(통합 메모리).** "GPU 메모리 부족"의 기준이 일반 그래픽카드와 다르며, 이 덕분에 후반부에 상당히 큰 모델도 다룰 수 있다.

이번 주 내내 기억할 구분: **하드닝은 호스트(컨테이너 밖)에서, 교재 실습은 컨테이너 안에서.**

## 1.2 미션 0 — 접속과 첫 세션

1. 배포받은 접속 정보로 SSH 접속한다 (직접 타이핑 허용 항목).
2. 터미널에 `claude`를 입력해 에이전트 세션을 시작한다.
3. 승인 요청 창의 구조(어떤 명령을 실행하려는지 표시됨)를 눈으로 익힌다.

첫 인사로 다음을 보내보자. 에이전트가 어떻게 행동하는지 관찰하는 것이 목적이다.

**📋 실행 프롬프트 P1-0**

```text
너는 이번 학기 내 실습 조수야. 이 시스템에서 네가 할 수 있는 일(파일 읽기/쓰기,
명령 실행)을 한 문단으로 설명하고, 지금 작업 디렉토리가 어디인지 pwd로 확인해서 알려줘.
```

## 1.3 미션 1 — 장비 파악: 내가 받은 것이 무엇인지 알기

**무엇을, 왜:** 시스템 사양을 조사해 문서로 남긴다. 목적은 두 가지다. 첫째, 앞으로의 모든 트러블슈팅은 "내 환경이 무엇인지"에서 출발한다. 둘째, "증거를 요구하는 프롬프트"의 첫 연습이다 — 각 항목에 확인 명령과 출력 원문을 함께 남기게 한다.

**📋 실행 프롬프트 P1-1**

```text
[목표] 이 시스템의 하드웨어·소프트웨어 사양을 조사해 spec-report.md로 정리
[포함 항목] CPU 아키텍처와 코어 수, 메모리 총량, GPU 모델명, 디스크 용량,
          OS 배포판과 버전, 커널 버전, NVIDIA 드라이버 버전, CUDA 버전, Docker 버전
[형식] 각 항목마다 3열 표로: 항목 | 확인에 사용한 명령 | 출력 원문(핵심 줄만)
[제약] 시스템 설정을 변경하는 명령은 사용하지 말 것(조회만)
[제약] 조회 명령은 `LC_ALL=C` 를 앞에 붙여 실행할 것.
       이 장비는 한국어 로케일이라 lscpu 등의 출력이 한글로 나온다.
       `lscpu | grep Architecture` 처럼 영어 필드명으로 grep 하면 아무것도 안 나온다
       (`LC_ALL=C lscpu | grep Architecture` 로 해결).
[산출물] spec-report.md 파일. 완료 후 파일 내용을 보여줄 것
```

**프롬프트 해설:** `[제약] 조회만` — 정보 수집 단계에서 시스템을 건드리지 못하게 막았다. 5원칙 중 ③제약, ④증거 적용.

**예상 결과:** 아키텍처 `aarch64`, 메모리 약 128GB(119GiB 내외로 표시될 수 있음), GPU `NVIDIA GB10`, OS는 Ubuntu 기반 DGX OS.

**결과 테스트 방법:** 보고서의 값이 실제와 일치하는지 에이전트에게 교차 검증시킨다. 에이전트가 만든 문서를 에이전트가 다시 검증하게 하는 이 패턴은 학기 내내 사용한다.

**✅ 검증 프롬프트 V1-1**

```text
spec-report.md의 각 항목을 방금 사용한 것과 다른 명령으로 다시 확인해서
교차 검증해줘. (예: 메모리를 free로 확인했다면 이번엔 /proc/meminfo로)
값이 다른 항목이 있으면 "항목 | 1차 값 | 2차 값 | 차이 원인" 표로 보고하고,
모두 일치하면 spec-report.md 끝에 "교차 검증 완료: 일시"를 추가해줘.
```

**통과 기준:** 아키텍처가 `aarch64`로 확인될 것. (여기서 `x86_64`가 나오면 접속한 장비가 잘못된 것이니 조교에게 문의.)

## 1.4 미션 2 — 최소 하드닝: 내 장비는 내가 지킨다

**무엇을, 왜:** 여러분의 Spark는 교내망에 연결된, 에이전트가 임의 코드를 실행하는 컴퓨터다. 사이버보안과 학생에게 무방비 서버 운영은 허용되지 않는다. 이번 미션은 4가지 최소 하드닝(SSH 키 인증 전환, 방화벽, fail2ban, 자동 보안 업데이트)을 **에이전트에게 안전하게 지시하는 법**을 함께 배운다.

> ⚠️ **경고: 이 미션은 실수하면 자기 장비에서 잠긴다(lockout).**
> 시작 전 반드시 **SSH 세션을 2개** 열어두라. 하나는 작업용, 하나는 비상용이다. 설정을 바꾼 뒤 비상용 세션이 살아있는 상태에서 새 접속을 테스트하고, 성공을 확인한 뒤에만 다음 단계로 간다.

### 1.4.1 SSH 키 인증 전환

**📋 실행 프롬프트 P1-2**

```text
[목표] SSH를 공개키 인증 전용으로 전환 (패스워드 로그인 비활성화)
[전제] 내 공개키는 ~/.ssh/authorized_keys에 이미 등록되어 있다 (없으면 먼저 알려줄 것)
[절차 제약 — 반드시 이 순서로]
 1. /etc/ssh/sshd_config를 백업 파일로 복사
 2. 현재 키 인증이 실제로 동작하는지 확인하는 방법을 나에게 안내하고, 내가
    "키 로그인 확인했음"이라고 답하기 전에는 절대 설정을 변경하지 말 것
 3. 내 확인 후: PasswordAuthentication no 로 변경
 4. sshd -t 로 문법 검사 → 통과 시에만 SSH 서비스 재시작
[검증] 변경 후 sshd -T | grep -i passwordauthentication 출력 첨부
[게이트] 각 단계 실행 전에 실행할 명령을 먼저 보여주고 내 승인을 받아라
```

**프롬프트 해설:** 이것이 5원칙 ⑤"게이트"의 표준형이다. 되돌릴 수 있게(백업), 안전을 확인한 뒤에만(내 확인 대기), 문법 검사를 통과해야만(sshd -t) 진행된다. 위험 작업 프롬프트는 항상 이 3요소를 갖춘다.

**결과 테스트 방법:** 비상용 세션을 유지한 채, 새 터미널에서 키로 접속되는지 / 패스워드 접속이 거부되는지 직접 확인한다(접속 시도는 타이핑 허용 항목).

### 1.4.2 방화벽, fail2ban, 자동 업데이트

**📋 실행 프롬프트 P1-3**

```text
[목표] 다음 3가지를 순서대로 적용
 1. UFW: SSH(22/tcp)만 허용하고 활성화. 나는 원격 접속 중이므로
    반드시 allow 규칙을 먼저 추가한 뒤 enable 할 것
    ⚠️ `ufw enable` 은 원격 접속 중이면 "Command may disrupt existing ssh
       connections. Proceed with operation (y|n)?" 라고 되묻는다.
       에이전트가 비대화형으로 실행하면 여기서 영원히 멈춘다.
       → `ufw --force enable` 을 쓰되, **allow 22/tcp 규칙이 이미 들어갔음을
         `ufw status` 로 확인한 뒤에만** 실행할 것.
 2. fail2ban 설치 후 sshd jail 활성화
 3. unattended-upgrades로 보안 업데이트 자동 적용 설정
[검증] 각 항목 완료 직후 다음 출력을 첨부:
 1. ufw status verbose
 2. fail2ban-client status sshd
 3. 자동 업데이트 설정 파일 내용과 서비스 상태
[게이트] 시스템을 변경하는 명령은 실행 전에 보여주고 승인받을 것
```

**예상 결과:** UFW `Status: active` + 22/tcp ALLOW, fail2ban의 sshd jail에 `Currently banned: 0`, 자동 업데이트 활성.

> ⚠️ **UFW는 Docker 컨테이너의 포트 노출을 막지 못한다.** Docker는 iptables의 `DOCKER` 체인에 직접 규칙을 넣어 UFW의 `INPUT` 체인을 우회한다. 즉 `docker run -p 8080:8080` 으로 띄운 서비스는 UFW가 `deny` 상태여도 외부에서 접속된다. 이번 학기 13주차에서 쓰는 Ollama도 기본값이 `0.0.0.0:11434` 라 모든 인터페이스에 열린다. 하드닝을 마친 뒤 반드시 `ss -tlnp | grep -E '11434|8080'` 로 실제 청취 주소를 확인하고, 외부 노출이 불필요한 서비스는 `-p 127.0.0.1:8080:8080` 처럼 루프백에 바인딩하라. "UFW가 켜져 있으니 안전하다"는 이 장비에서 **거짓**이다.

**결과 테스트 방법 — 종합 점검 문서화:** 하드닝은 "했다"가 아니라 "증명 가능하다"가 기준이다. 아래 검증 프롬프트로 체크리스트 문서를 만든다. 이 문서가 추가 제출물이다.

**✅ 검증 프롬프트 V1-2**

```text

[점검 항목과 증거 명령]
 1. 패스워드 로그인 비활성 — sshd -T | grep -i passwordauthentication
 2. 열린 TCP 포트 목록 — ss -tlnp (22 외의 외부 노출 포트가 있으면 표시)
 3. 방화벽 상태 — ufw status verbose
 4. fail2ban 동작 — fail2ban-client status sshd
 5. 자동 보안 업데이트 — 관련 설정 파일과 타이머 상태
[형식] 항목 | 기대 상태 | 증거 명령 | 실제 출력 | 판정(PASS/FAIL) 5열 표

      수정은 내가 지시한다.
```

**통과 기준:** 5개 항목 전부 PASS. FAIL이 있으면 원인을 읽고, 수정 지시 프롬프트를 여러분이 직접 작성해 해결한 뒤 재점검한다.

> ⚠️ **ch02.ipynb 에는 의도적으로 실패하는 셀이 들어 있다.** 2장은 "어휘에 없는 단어를 넣으면 KeyError 가 난다"는 OOV 문제를 보여주려고 **일부러 예외를 발생시키는 셀**을 포함한다(여러분이 2.4절 P2-4 에서 직접 만나게 될 그 오류다). 따라서 `nbconvert --execute` 를 그냥 돌리면 **반드시 그 셀에서 멈춘다.**
>
> 이것은 환경 문제가 아니므로 "해결 방안"을 찾을 대상이 아니다. 스모크 테스트의 목적은 "**의도된 실패를 제외한 나머지 셀이 전부 도는가**"를 확인하는 것이다. 따라서 실행 명령에 `--allow-errors` 를 붙이고, 실행 후 오류가 난 셀이 **의도된 그 셀 하나뿐인지**를 확인하는 것까지가 이 미션이다.
>
> ```bash
> jupyter nbconvert --to notebook --execute --allow-errors \
>   --output ch02_executed.ipynb ch02.ipynb
> ```
> 그리고 실행된 노트북에서 오류 셀을 세어 보고하게 하라 — 오류가 2개 이상이면 그때는 진짜 환경 문제다.
>
> **여기서 배울 것:** 에이전트에게 "무결 실행"만 시키면, 에이전트는 통과시키려고 그 셀을 지우거나 고치려 든다(교재 코드를 훼손하는 것이다). "무엇이 실패해도 되는가"를 먼저 정의하는 것이 검증 설계의 절반이다.

**프롬프트 해설:** `해결 방안 2가지 이상 제시 후 대기` — 문제 해결의 선택권을 여러분이 갖는 구조다. 에이전트가 제시한 선택지를 비교·선택하는 것이 이 수업에서 말하는 "실습"이다.

**예상 결과:** 정상이라면 오류 없이 완료. 오류가 난다면 대부분 패키지 누락/버전 문제이며, 에이전트의 원인 분석에서 "aarch64", "CUDA", "버전" 같은 단어가 왜 등장하는지 1.1절과 연결해 생각해보라.

## 2.1 배경 이론

**왜 토큰인가.** 신경망은 숫자만 계산한다. 따라서 LLM의 첫 단계는 텍스트를 잘게 쪼개고(토큰화), 각 조각에 정수 ID를 붙이는 일이다. 이번 주는 이 "텍스트 ↔ ID" 왕복 변환기를 두 번 만든다: 한 번은 원리를 보기 위해 단순하게, 한 번은 실제 GPT-2가 쓰는 방식(BPE)으로.

**단순 토크나이저 파이프라인.** ① 정규식으로 단어·구두점 분리 → ② 고유 토큰을 정렬해 사전(vocabulary: 토큰→ID) 구축 → ③ encode(텍스트→ID 목록), decode(ID 목록→텍스트) 구현. 이 방식의 치명적 한계: **사전에 없는 단어(OOV)를 만나면 처리 불가.** 훈련 텍스트에 "Hello"가 없었다면 "Hello"는 인코딩조차 못 한다.

**특수 토큰.** OOV를 임시로 막는 방법이 `<|unk|>`(모르는 단어 대체)다. 또 서로 무관한 문서를 이어 붙일 때 경계 표시로 `<|endoftext|>`를 쓴다. GPT-2는 실제로 `<|endoftext|>`를 사용한다.

**BPE(Byte Pair Encoding).** 근본 해법은 단어보다 작은 단위(서브워드)다. BPE는 훈련 코퍼스에서 자주 붙어 나오는 문자쌍을 반복 병합해 어휘를 만든다. 자주 나온 단어는 통짜 토큰이 되고, 처음 보는 단어는 아는 조각들로 분해된다 — 그래서 **OOV가 원리적으로 없다.** GPT-2의 BPE 어휘 크기는 50,257개다: 바이트 256개 + 병합 토큰 50,000개 + `<|endoftext|>` 1개. 우리는 이를 구현한 `tiktoken` 라이브러리를 쓴다.

**한국어와 BPE.** GPT-2의 병합 규칙은 영어 중심 코퍼스에서 학습됐다. 한글은 UTF-8에서 글자당 3바이트인데, 한국어 바이트 조합은 병합 학습이 덜 되어 있어 **같은 의미의 문장이 영어보다 훨씬 많은 토큰으로 쪼개진다.** 이것이 무엇을 의미하는지(비용, 컨텍스트 창 소모) 이번 주 마지막 실험에서 직접 측정한다.

**무엇을, 왜:** 토큰 목록에서 사전을 만들고, encode/decode를 갖춘 첫 토크나이저 클래스를 만든다. 그리고 **일부러 실패를 경험한다** — 이 실패가 다음 미션의 존재 이유다.

**📋 실행 프롬프트 P2-2**

```text

[할 일]

    - decode(self, ids) -> str: 공백으로 잇되, 구두점 앞의 불필요한 공백은
      정규식으로 제거
```

**📋 실행 프롬프트 P2-3** — 왕복 테스트

```text
tokenizer_v1.py의 SimpleTokenizerV1로 다음을 테스트해줘:
[입력 문장] "It's the last he painted, you know," Mrs. Gisburn said with pardonable pride.
[할 일] ① encode 결과 ID 리스트 출력 ② 그 ID를 다시 decode한 문자열 출력
       ③ 원문과 decode 결과가 일치하는지 비교 (차이가 있다면 어디가 다른지)
[제약] 일치하지 않아도 코드를 고치지 말 것. 왜 다른지만 설명하라.
```

**예상 결과 (정답지):** **원문이 그대로 복원되지 않는다.** 이것이 정상이다.

```
원문   : "It's the last he painted, you know," Mrs. Gisburn said with pardonable pride.
decode : " It' s the last he painted, you know," Mrs. Gisburn said with pardonable pride.
```

두 군데가 다르다. 첫째, 문장 앞에 **공백 하나**가 붙었다. 둘째, `It's` 가 **`It' s`** 로 벌어졌다.

**왜 그런가.** V1 의 decode 는 토큰을 공백으로 이어 붙인 뒤(`" ".join(...)`) 구두점 앞의 공백만 정규식으로 지운다. 그런데 `'` 는 그 정규식의 대상 문자 목록에 있어 `It '` → `It'` 로 붙지만, 그 **뒤에 오는 `s` 앞의 공백은 지울 규칙이 없다.** 토크나이저가 `It` / `'` / `s` 셋으로 쪼개는 순간, 원문의 띄어쓰기 정보는 **이미 사라졌다.**

**통과 기준:** decode 결과가 원문과 다르다는 것을 **정확히 두 지점**(선행 공백, `It' s`)으로 특정하고, 그 원인을 "토큰화 과정에서 공백 정보가 소실되기 때문"으로 설명할 것.

> **여기서 배울 것:** 토큰화는 **손실 변환**이다. 이 사실이 왜 중요한가 — 2.6절에서 만날 BPE 는 정반대로 설계되어 있다. GPT-2 BPE 는 공백을 토큰 **안에** 넣어(`" the"` 처럼 선행 공백 포함) 완전 복원을 보장한다. V1 의 이 실패가 BPE 설계의 이유다.
>
> 그리고 검증 습관 하나: **"통과 기준"에 적힌 것이 실제로 통과하는지 의심하라.** 교재 저장소 `ch02.ipynb` 의 저장된 출력에도 `" It' s"` 가 그대로 찍혀 있다. 정답지가 틀릴 수 있다.

**📋 실행 프롬프트 P2-4** — 의도된 실패

```text
같은 토크나이저로 이번엔 "Hello, do you like tea?" 를 encode해봐.
오류가 나면: 오류 전문을 보여주고, 왜 이 오류가 발생했는지 어휘사전과
연결해서 설명해줘. 아직 코드를 고치지는 마.
```

**프롬프트 해설:** `아직 고치지 마` — 실패를 관찰 대상으로 고정하는 지시다. 에이전트는 시키지 않으면 오류를 즉시 고쳐버리는 경향이 있고, 그러면 여러분은 "왜 실패하는가"를 생각할 기회를 잃는다.

**예상 결과:** `Hello`가 사전에 없어 KeyError 발생. 훈련 텍스트(단편소설)에 없던 단어이기 때문이다. 이것이 OOV 문제다.
