## 9.1 배경 이론

**손실 = "정답 토큰에 준 확률"의 벌점.** 모델의 로짓에 softmax를 씌우면 5만 개 토큰에 대한 확률분포가 나온다. 좋은 모델이라면 **실제 다음 토큰**에 높은 확률을 줬을 것이다. 크로스 엔트로피 손실은 정답 토큰의 확률에 log를 취하고 부호를 뒤집은 것의 평균이다 — 정답에 확률 1을 주면 손실 0, 확률이 낮을수록 손실이 치솟는다.

**훈련 전 손실은 예측 가능하다.** 7주차에서 봤듯 무작위 모델의 확률분포는 거의 균등하다. 균등분포가 정답에 주는 확률은 1/50,257이므로 손실은 −ln(1/50257) = **ln(50257) ≈ 10.82**. 즉 훈련 전 손실은 대략 10.8 근처여야 하고, 이 값에서 크게 벗어나면 코드가 틀린 것이다. 손실 함수를 짜자마자 검증할 수 있는 정답지가 이론에서 공짜로 나온다.

**퍼플렉시티.** exp(손실). "모델이 매 순간 몇 개의 후보 사이에서 고민하는가"로 읽힌다. 훈련 전엔 exp(10.79) ≈ 48,726 — 사실상 어휘 전체(50,257개)를 놓고 찍고 있다는 뜻이다.

**train/val 분리.** 훈련에 쓰지 않은 검증 데이터의 손실이 진짜 실력이다. 훈련 손실만 보면 "암기"와 "학습"을 구분할 수 없다. 이번 주의 하이라이트는 그 둘이 갈라지는 순간(과적합)을 곡선과 물증으로 잡는 것이다.

**훈련 루프.** [배치 순전파 → 손실 → 역전파 → AdamW 갱신]을 돌며, 일정 주기로 train/val 손실을 평가하고 매 에폭 샘플 문장을 생성해 눈으로도 진행을 본다. 훈련용 config는 context_length를 1024에서 **256으로 줄인다** — 작은 데이터셋에서 훈련 부담을 줄이기 위한 교재의 선택이다.

## 9.3 미션 1 — 손실 해부: softmax부터 ln(50257)까지

**무엇을, 왜:** `F.cross_entropy` 한 줄을 쓰기 전에, 그 안에서 벌어지는 일을 단계별로 직접 재구성한다. 그리고 **이론이 예언한 초기 손실값**과 대조한다.

**📋 실행 프롬프트 P9-1**

```text
[목표] 크로스 엔트로피를 확률 단계부터 수동 재구성 (교재 5.1.2절)
[할 일] week09/loss_anatomy.py 작성·실행:
 1. torch.manual_seed(123), context_length=256으로 줄인 GPT_CONFIG_124M
    모델 생성, eval 모드
 2. 예제 배치: inputs = [[16833, 3626, 6100], [40, 1107, 588]]
    ("every effort moves" / "I really like"),
    targets = [[3626, 6100, 345], [1107, 588, 11311]]
 3. 단계별 계산·출력:
    a. 로짓 → softmax → 확률 텐서 shape
    b. 각 위치에서 "정답 토큰이 받은 확률" 6개 추출
    c. log 적용 → 평균 → 부호 반전 = 수동 손실
    d. F.cross_entropy(logits.flatten(0,1), targets.flatten()) = 자동 손실
 4. 퍼플렉시티 = exp(손실) 출력
[검증] c와 d가 소수 4자리까지 일치하는지 명시할 것
```

**예상 결과 (정답지):** 수동 손실 = 자동 손실 ≈ **10.7940**, 퍼플렉시티 ≈ **48,726**. (GPU 부동소수 특성상 끝자리 미세 차이는 허용.)

**결과 테스트 방법 (직접 손계산):** ln(50257)을 계산해(≈ **10.825**) 측정값 10.794와 나란히 적어라. "훈련 전 모델 ≈ 균등분포 찍기"가 숫자로 증명된다. 정답 토큰이 받은 확률 6개도 눈으로 보라 — 대략 1/50257 = 0.00002 근처의 먼지 같은 값들일 것이다.

**해석 과제 (report.md에 본인이 직접 작성 — 에이전트 사용 금지):** val 손실이 내려가다 멈추고 train과 벌어지는 이유를 데이터 크기(5,145토큰)와 모델 크기(1.63억 파라미터)의 대비로 3~5문장 설명하라. 그리고 7주차 타임캡슐에 적었던 예상과 실제 결과를 대조하라.

## 9.6 미션 4 — 속도 실험: Spark의 첫 몸풀기

**무엇을, 왜:** 같은 훈련을 CPU·GPU·bf16으로 돌려 시간을 잰다. 그리고 "GPU를 충분히 먹이면" 무슨 일이 생기는지 배치 크기를 키워 처리량으로 확인한다 — 앞으로 큰 훈련(11~13주)의 설정 감각이 여기서 생긴다.

**📋 실행 프롬프트 P9-4**

```text
[목표] 훈련 속도 비교 실험
[할 일] 실험 스크립트 작성·실행, 결과를 week09/speed_report.md 표로 저장:
 [실험 A — 장치 비교] 동일 설정(1 에폭, batch=2)으로 3회씩 측정, 평균:
  1. CPU
  2. GPU (fp32)
  3. GPU + bf16 autocast (forward·손실만 autocast, 옵티마이저는 기본)
 [실험 B — GPU 처리량] GPU fp32에서 batch_size ∈ {2, 8, 32}로
  1 에폭 시간과 초당 처리 토큰 수(tokens/sec) 측정
  ⚠️ 이 실험만 stride=128 로 바꿔 로더를 다시 만들 것.
     P9-2 설정(max_length=stride=256)으로는 train 샘플이 18개뿐이라
     batch=32 에서 drop_last=True 가 배치를 **0개**로 만든다 —
     루프가 아예 돌지 않아 tokens/sec 가 0 이거나 ZeroDivisionError 가 난다.
     stride=128 이면 샘플이 35개가 되어 세 조건 모두 측정된다.
     (3주차 그리드 표의 (256,128) 행이 바로 이 설정이다 — 중복 128 토큰)
     로더를 만든 직후 `len(loader)` 를 세 조건 모두 출력해 확인할 것.
[측정 규약] GPU 측정은 워밍업 1회 후 시작, 시작·종료 시
  torch.cuda.synchronize(). 각 실험 사이 모델·옵티마이저 재생성(시드 고정)
[형식] 표 A: 장치 | 1에폭 시간(s) | CPU 대비 배속
      표 B: batch | 시간(s) | tokens/sec | batch=2 대비 처리량 배율
[검증] 표 B에서 batch를 키울 때 tokens/sec가 어떻게 변하는지 짚고,
      "이 모델·데이터가 GPU를 충분히 활용하고 있는가"에 대한 판단을
      근거와 함께 한 문단으로 쓸 것
```

**예상 결과:** GPU가 CPU 대비 수 배~수십 배(참고 실측 GB10: **11.5배**). bf16의 이득은 이 규모(124M, ctx 256, batch 2)에선 **크지 않을 수 있다** — 배치가 작아 GPU가 놀고 있기 때문이다(참고 실측 1.13배). 표 B에서 batch를 키우면 에폭 시간은 큰 차이 없이 tokens/sec가 뛰어오르는 것을 보게 된다(참고 실측 stride=128 기준 4,155 → 7,166, **1.72배**): **작은 배치는 GPU를 굶긴다.** 이 관찰이 이후 모든 훈련에서 배치·정밀도를 정하는 근거가 된다.

**해석 과제 (본인 작성):** "모델 적재 621MB(7주차)면 충분한 줄 알았는데 훈련은 왜 메모리가 더 필요한가?" — 기울기, 옵티마이저 상태(AdamW는 파라미터당 2개), 활성값의 존재를 들어 3~4문장으로 설명하라. (`nvidia-smi`로 훈련 중 메모리를 직접 관찰해 근거로 삼아도 좋다.)

## 10.1 배경 이론

**greedy의 한계.** 매번 1등 토큰만 뽑으면 출력이 결정적이고 단조로우며, 같은 구절을 맴도는 반복 루프에 빠지기 쉽다. 대안은 확률분포에서 **추첨**하는 것(`torch.multinomial`) — 2등, 3등에게도 확률만큼 기회를 준다.

**temperature.** 추첨의 과감함을 조절하는 다이얼이다. softmax에 넣기 전 **로짓을 T로 나눈다**: T < 1이면 큰 로짓이 더 커져 분포가 뾰족해지고(보수적), T > 1이면 차이가 눌려 평평해진다(모험적). T → 0 극한은 greedy와 같아진다. 4주차 √d 스케일링 실험에서 "나누는 수가 softmax 분포를 바꾼다"를 이미 봤다 — 같은 원리를 이번엔 의도적으로 이용하는 것이다.

**top-k.** 아무리 평평해도 5만 개 전부에게 기회를 주면 가끔 완전한 헛소리가 뽑힌다. 상위 k개만 남기고 나머지 로짓을 −inf로 채우면(5주차의 그 −inf 트릭이다 — softmax에서 정확히 0이 된다) 추첨 후보를 품질 좋은 상위권으로 제한할 수 있다. 실전에서는 top-k로 후보를 자르고 temperature로 그 안의 과감함을 조절하는 조합을 쓴다.

**체크포인트.** `state_dict`(파라미터 사전)를 저장·로드한다. **이어서 훈련**하려면 모델만으로는 부족하다 — AdamW는 파라미터마다 관성 상태 2개를 들고 있으므로(9주차 메모리 문제의 그 상태들), 옵티마이저 state_dict도 함께 저장해야 끊긴 자리에서 매끄럽게 이어진다.

**공개 가중치 이식.** OpenAI가 공개한 GPT-2 가중치를 우리 구현에 옮겨 싣는다. 구조가 같아도 저장 방식이 다르면 그대로는 안 들어간다: OpenAI 체크포인트는 Q·K·V가 한 행렬에 합쳐져 있어 **셋으로 쪼개야** 하고, Linear 가중치의 **전치**(4주차 연습문제 3.1에서 겪은 바로 그 문제), 그리고 원본은 **qkv_bias=True**·context 1024라는 설정 차이가 있다. "가중치 이식 = 두 구현의 규약을 맞추는 일"이라는 감각이 이번 주의 숨은 수확이다.

|---|---|---|---|
| **0.5** | 6단어 / 11% | 6단어 / 11% | 6단어 / 11% |
| **1.0** | 3단어 / 31% | 3단어 / 17% | 6단어 / 20% |
| **1.4** | 3단어 / 38% | 4단어 / 18% | 3단어 / 36% |

> top_k 의 효과는 T 가 클 때 뚜렷해진다(위 표의 1.4 행: k=None 이탈 38% vs k=25 이탈 18%). 이것이 **"top_k 는 헛소리의 하한선을 막는 안전장치이고, 문체를 바꾸는 다이얼은 T"** 라는 말의 실측 근거다.

## 10.7 미션 5 — OpenAI 가중치 이식: 남의 체크포인트 싣기

**무엇을, 왜:** OpenAI GPT-2 공개 가중치를 우리 구현에 로드한다. 순서가 중요하다: **124M로 절차를 검증한 뒤 355M로 확장**한다(작게 검증, 크게 실행 — 이후 모든 스케일업의 표준 절차다). 마지막으로 연습문제 5.5 — 사전 훈련된 모델의 the-verdict 손실을 측정해 우리 모델과 정면 비교한다.

**📋 실행 프롬프트 P10-5**

```text
[목표] OpenAI GPT-2 가중치 로드 (교재 5.5절)
[할 일] week10/openai_load.py 작성:
 1. 가중치 다운로드 — 경로를 반드시 지정할 것
    ⚠️ ch05/01_main-chapter-code/gpt_download.py 는 `import tensorflow` 로
       시작한다. llm-lab 골든 이미지에 tensorflow 가 없으므로 그대로는
       ModuleNotFoundError 가 난다. 이것이 정상이다.
    → ch05/02_alternative_weight_loading/**weight-loading-hf-safetensors.ipynb**
       의 방식을 쓴다. 컨테이너에서 먼저 `pip install safetensors` 를 실행하고,
       HuggingFace 허브에서 model.safetensors(124M 548MB)를 직접 받아
       텐서만 읽는다.
    🚫 같은 폴더의 weight-loading-pytorch.ipynb 는 **쓰지 말 것.**
       그 .pth 는 이미 우리 구현의 키 이름으로 변환돼 있어 한 줄로 실린다
       (`load_state_dict(torch.load(...))` 가 strict=True 로 통과한다).
       QKV 분할도 전치도 필요 없어져 아래 3번의 학습 목표가 통째로 사라진다.
 2. config 조정: context_length=1024, qkv_bias=True 로 우리 GPTModel 생성
 3. 교재의 load_weights_into_gpt 로직을 참고해 가중치를 이식하되,
    다음 두 지점에서 "왜 이런 처리가 필요한지" 주석으로 설명할 것:
    a. 합쳐진 QKV 행렬을 셋으로 분할하는 부분

    같은 프롬프트 생성과 val 손실 측정
[검증] 두 모델 모두 생성문이 자연스러운 영어인지, val 손실이 우리
      10에폭 모델(≈6점대)과 비교해 어떤지 명시할 것
```

**예상 결과:** 로드된 모델은 훈련 없이도 유창한 영어를 생성한다. the-verdict **val 손실은 3점대 중반** — 이 소설을 한 번도 본 적 없는 모델이, 이 소설로 10에폭 훈련한 우리 모델(val ≈ 6점대)을 압도한다. **일반화는 큰 데이터에서 나온다**는 이번 학기 최대의 정량 증거다.
