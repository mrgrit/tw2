# 14주차. 팀 프로젝트 주간 — 정답지 없는 첫 주

## 14.0 개요

| 항목 | 내용 |
|---|---|
| 편성 | 2인 1조 권장 (트랙 D는 2인 필수 — 장비 2대) |
| 일정 | 월: 제안서 마감·승인 / 수업일: 스탠드업 + 공개 디버깅 / 금: 결과 제출 |
| 제출물 | 제안서 1쪽, 구현(팀 저장소), 결과 리포트, 개인별 프롬프트 로그 |
| 평가 철학 | **목표 달성도보다 실험 설계와 실패 분석의 질** |

## 14.1 이번 주가 다른 이유

지금까지 교재가 정답지(4,690 토큰, 163,009,536 파라미터, "Featureiman...")를 줬다. 이번 주부터는 **성공 기준을 여러분이 정의**하고, 그 기준을 통과했음을 여러분의 검증으로 입증한다. 다행히 빈손이 아니다 — 한 학기 동안 쌓은 자산이 있다:

- **성질 테스트**: 인과성 불변(5·6주), greedy 결정성(7주), top-k 제약(10주), LoRA 항등 게이트(13주)
- **품질 게이트**: "돌아간다"가 아니라 손실·동일성으로 판정(10주 이식, 13주 LoRA)
- **절차**: 작게 검증 → 크게 실행(10주), 점검·조치 분리, 계획·승인 게이트(1주)
- **측정 규약**: synchronize·워밍업·tokens/sec(9주), peak 메모리(11주)

프로젝트 평가표의 절반은 사실상 "이 자산들을 자기 문제에 이식했는가"를 본다.

## 14.2 트랙 카드

각 트랙의 출발 자료는 교재 저장소(`rickiepark/llm-from-scratch`)의 해당 장 보너스 폴더다. 마일스톤은 3단계로 적었다 — **최소(통과선) / 기대(표준) / 도전(가산)**.

### 트랙 A — 아키텍처: KV 캐시 (또는 GQA·MLA·SWA 중 1)

- **목표**: 생성 시 매 토큰 전체 재계산의 낭비(5주차 문제 5, 7주차 문제 3)를 캐시로 제거
- **마일스톤**: 최소 — KV 캐시 동작 구현 / 기대 — 캐시 on·off의 greedy 출력 **완전 동일성 게이트** 통과 + 생성 길이별 속도 벤치마크 / 도전 — GQA 등 변형 1종 추가 비교
- **검증 기준**: 동일성 게이트(출력이 1토큰이라도 다르면 실패) + tokens/sec 곡선
- **주의**: 캐시 자료구조의 context 초과 처리 — 7주차 크롭 테스트를 이식하라

### 트랙 B — 최신 모델 재현: Llama 3.2 / Qwen3 / Gemma 3 from scratch

- **목표**: GPT-2와 최신 아키텍처의 구조적 차이(RoPE, RMSNorm, GQA 등)를 코드로 확인
- **마일스톤**: 최소 — 보너스 구현 구동 + 구조 차이표(GPT-2 대비 부품별) / 기대 — 공개 가중치 로드 후 유창한 생성(10주차 이식 절차 재사용) / 도전 — 동일 프롬프트로 GPT-2 355M과 정성·정량 비교
- **검증 기준**: 로드 후 생성 품질 + 파라미터 분해표(7주차 방식)를 새 모델에 재작성
- **주의**: 토크나이저가 다르다 — 2주차 감각으로 어휘·특수 토큰부터 파악하라

### 트랙 C — 정렬: DPO 밑바닥 구현

- **목표**: 선호쌍(chosen/rejected)으로 응답 품질을 한 단계 끌어올리기
- **마일스톤**: 최소 — DPO 손실 구현 + 소규모 선호 데이터 구성 / 기대 — 13주차 SFT 모델에 DPO 적용, 저지 평균 점수 향상 입증 / 도전 — 선호 데이터를 13주차 저지로 자동 생성(두 응답 중 승자 고르기)하는 파이프라인
- **검증 기준**: 저지 점수 전후 비교(13주차 신뢰성 검증을 통과한 저지로) + DPO 손실 곡선
- **주의**: 참조 모델 동결을 잊으면 손실이 무의미해진다 — LoRA 항등 게이트류의 시작점 검증을 설계하라

### 트랙 D — 분산 훈련: Spark 2대 연결 (2인 필수)

- **목표**: 부록 A의 DDP 스크립트로 멀티노드 사전 훈련, "2대 = 몇 배?"를 실측
- **마일스톤**: 최소 — 2대 네트워크 연결 + 단일 노드 DDP(1대 안 GPU 1개지만 프로세스 검증) / 기대 — 2노드 훈련 성공 + 1대 대비 tokens/sec 배율 측정(9주차 규약) / 도전 — 구텐베르크급 데이터로 동일 시드 손실 궤적의 1대·2대 비교
- **검증 기준**: 처리량 표 + 손실 궤적이 합리적으로 겹치는지
- **주의**: 사전에 조교에게 연결 키트(케이블·설정 가이드) 수령. 네트워크 설정은 1주차 하드닝과 충돌하지 않게 — 방화벽 규칙 추가를 "계획·승인 게이트"로 진행하라

### 트랙 E — 서빙: 내 모델의 챗 UI

- **목표**: 13주차 튜닝 모델을 스트리밍 챗 서비스로
- **마일스톤**: 최소 — 로컬 API + 단순 UI에서 대화 / 기대 — 토큰 스트리밍, eos 종료, 대화 이력의 컨텍스트 관리(크롭 정책 명시) / 도전 — 동시 사용자 2인 이상 처리 + 간단한 부하 측정
- **검증 기준**: 시연 시나리오 완주 + 컨텍스트 초과 상황의 의도된 동작
- **주의**: 사이버보안과답게 — 교내망 노출 범위와 입력 검증을 리포트에 한 절로

### 트랙 F — 자율 (도메인 응용, 승인 필요)

- **예시**: 보안 로그 분류기(11주차 파이프라인 이식), 시큐리티 QA 지시 튜닝(12–13주차 이식 + 자체 데이터 구축), 피싱 문자 탐지(11주차 + 한국어 토큰 문제 정면 돌파)
- **조건**: 제안서에 **성공 기준을 정량으로 자체 정의**하고 교수 승인을 받을 것
- **주의**: 데이터 구축이 절반 이상의 일이다 — 12주차 품질 점검을 자기 데이터에 반드시 적용하라

## 14.3 제안서 (1쪽, 월요일 마감)

**템플릿:**

```markdown
# 팀명 / 트랙 / 팀원(역할)
## 1. 목표 (2~3문장)
## 2. 성공 기준 (정량 — 무엇을 측정해 얼마면 성공인가)
## 3. 마일스톤: 최소 / 기대 / 도전
## 4. 역할 분담 (누가 어떤 미션의 지시·검증을 맡나)
## 5. 리스크 상위 3개와 플랜 B
```

제안서 초안을 잡은 뒤, 아래 프롬프트로 **스트레스 테스트**하라. 주의 — 에이전트에게 주제를 정하게 하면 안 된다. 아이디어는 팀의 것, 에이전트는 그 아이디어를 두들겨보는 망치다.

**📋 프롬프트 P14-1 — 사전 부검(pre-mortem)**

```text
[역할] 너는 이 제안서의 회의적인 심사위원이다
[입력] (제안서 붙여넣기)
[할 일]
 1. "이 프로젝트가 금요일에 실패했다"고 가정하고, 가장 그럴듯한 실패
    원인 5개를 구체적으로 서술해줘 (기술·일정·협업 각 1개 이상)
 2. 각 원인마다: 화요일에 감지할 수 있는 조기 신호 1개와 예방 조치 1개
 3. 성공 기준(2번 항목)이 검증 가능하게 쓰였는지 비판해줘 —
    측정 방법이 빠졌으면 지적할 것
[제약] 대안 주제를 제안하지 말 것. 이 주제 안에서만 비판하라
```

## 14.4 팀 협업 규약

- 팀 저장소 1개(브랜치로 분업), 개인 프롬프트 로그는 **각자** `prompts_<이름>.md`로 — 개인 기여의 증빙이자 개인 평가 근거다.
- 커밋 작성자 = 그 작업을 **지시·검증한 사람**. 에이전트가 짰어도 책임자는 사람이다.
- 매일 마지막 작업 후 push (1주차 CLAUDE.md 규칙은 팀 저장소에도 심을 것).

## 14.5 수업 시간 운영

- **스탠드업(팀당 90초)**: 어제 한 것 / 오늘 할 것 / 막힌 것. 막힌 것이 없다고 말하는 팀에게는 교수가 성공 기준을 캐묻는다.
- **공개 디버깅("프롬프트 회진")**: 가장 흥미롭게 막힌 팀이 화면을 공유하고, 전원이 "다음에 던질 프롬프트"를 제안한다. 채택된 프롬프트가 문제를 풀면 제안자에게 참여 점수. 막힘은 부끄러운 것이 아니라 이 수업의 교보재다.

## 14.6 채점 루브릭 (프로젝트 결과물)

| 항목 | 배점 | 기준 |
|---|---|---|
| 실험 설계 | 30 | 성공 기준의 정량성, 통제 변인, 학기 자산(게이트·성질 테스트)의 이식 |
| 검증과 실패 분석 | 30 | 주장마다 증거가 붙었는가. 실패를 원인 수준까지 파고들었는가 (실패 자체는 감점이 아니다) |
| 결과 완성도 | 20 | 마일스톤 도달 수준 (최소 통과 = 12, 기대 = 17, 도전 = 20) |
| 협업·로그 | 10 | 개인 로그의 실재성, 역할 분담의 균형 |
| 회고 정합성 | 10 | 제안서의 리스크 예측과 실제의 대조 |

## 14.7 교수·조교용 메모

*학생 배포본에서는 이 절을 제거할 것.*

- 트랙 D 사전 준비: 연결 키트(케이블/스위치), 노드 간 IP 대역과 방화벽 예외 가이드 문서, DDP 런처 예시. 신청 팀 수만큼 키트 확보(개강 전 체크리스트 항목).
- 승인 기준: 성공 기준이 측정 불가능하면 반려(예: "성능을 개선한다" → 반려, "동일 출력 게이트 통과 + 512토큰 생성에서 1.5배 이상" → 승인).
- 전형적 함정: A — 캐시 출력 불일치를 "거의 같음"으로 넘기려는 시도(불허), C — 참조 모델 미동결, D — 방화벽에 막힌 통신을 코드 문제로 오인(1주차 하드닝 리마인드), F — 데이터 구축 과소평가(화요일까지 데이터 미확보면 플랜 B 발동 권고).

# 15주차. 발표회 — 내가 키운 LLM

## 15.0 형식

| 항목 | 내용 |
|---|---|
| 발표 | 팀당 18분: 라이브 시연 10 + 회고 5 + Q&A 3 |
| 시연 | **자기 Spark에서 라이브 필수** (녹화는 장애 대비 백업으로만) |
| 개인 제출 | 기말 리포트 2쪽 + 동료 평가 |

## 15.1 시연 규칙

- 콜드 스타트를 밝혀라: 미리 띄워둔 것(모델 로딩 등)과 현장에서 실행하는 것을 시작할 때 구분해 선언한다.
- **시연 중 실패는 감점이 아니다 — 대응이 평가다.** 침착하게 원인을 좁히는 3분(로그 확인 → 가설 → 우회)은 오히려 가산 대상이다. 한 학기 내내 연습한 것이 바로 그것이다.
- 시연 시나리오에는 반드시 "검증의 순간"을 하나 넣어라 — 게이트 통과, 성질 테스트 실행, 전후 비교 수치 등. 데모는 쇼가 아니라 증명이다.

## 15.2 리허설

**📋 프롬프트 P15-1 — 시연 드라이런**

```text
[목표] 발표 시연 리허설과 리스크 점검
[입력] 시연 시나리오(단계별 명령·기대 화면)를 붙여넣는다
[할 일]
 1. 시나리오를 처음부터 끝까지 실제로 실행하며 각 단계의 **명령 실행 시간**을
    측정하고, 각 단계에 필요한 **설명 시간**을 별도로 산정해
    (실행 + 설명) 합계를 내라. 합계가 10분을 넘으면 어디를 줄일지 제안해줘
    ⚠️ 명령 실행 시간만으로는 10분을 넘기 어렵다 (Spark 기준 참고 실측:
       8단계 시나리오 총 11~14초). 발표의 병목은 사람의 말이지 GPU 가 아니다.
       각 단계에 "이 화면에서 무엇을 말할 것인가"를 한 줄씩 적고,
       그 분량을 분당 300자로 환산해 설명 시간을 잡아라.
 2. 리스크 점검: 모델 로딩 시간, 첫 토큰 지연, 네트워크 의존 단계,
    이전 실행의 잔여 상태(캐시·포트 점유)를 각각 확인하고 완화책 제시
 3. "발표 5분 전 체크리스트"를 명령어 수준으로 만들어줘
[검증] 드라이런을 한 번 더 반복해 두 실행의 소요 시간 차이를 보고할 것
```

## 15.3 회고 5분 가이드

다음 네 질문에 실물 증거(로그·프롬프트 원문)로 답하라. 소감문이 아니라 기술 회고다.

1. 이번 학기 **가장 효과적이었던 프롬프트 패턴 1개** — 실제 프롬프트를 화면에 띄우고, 왜 통했는지 설명
2. **최악의 지시 1개**와 그것이 만든 사고, 그리고 얻은 교훈
3. 에이전트가 **끝내 잘 못하더라**는 것 1개 — 발견 경위 포함
4. 다시 시작한다면 1주차의 나에게 해줄 조언 한 문장

## 15.4 동료 평가 (팀당 1분, 전원 제출)

| 항목 | 5점 기준 |
|---|---|
| 명확성 | 무엇을 왜 했는지 비전공 친구에게도 통할 수준 |
| 검증 신뢰성 | 주장에 증거가 붙어 있고, 게이트/테스트가 실물로 돌았다 |
| 시연 완성도 | 시나리오 완주 또는 실패 시 훌륭한 대응 |
| 회고 깊이 | 실물 증거 기반, 자기비판 포함 |

- +한 줄 코멘트(필수): "이 팀에서 훔치고 싶은 것 하나".
- **환산 규칙**: 항목 4개 평균(5점 만점) → 팀별로 **자기 팀을 제외한** 전체 학생 평균을 내고, 상·하위 각 10%를 절사한 뒤 15.6절의 5% 만점으로 선형 환산한다. (극단값 절사는 담합·보복 평가의 영향을 줄이기 위한 것이다.)

   - 부록 B 검증 패턴에 추가하고 싶은 "나만의 패턴" 1개 (이름 붙이기)

## 15.7 학기 마무리 — 저장소를 포트폴리오로

마지막 미션이다. 한 학기의 저장소를 남에게 보여줄 수 있는 상태로 만든다.

**📋 프롬프트 P15-2 — 아카이빙**

```text
[목표] 과제 저장소를 포트폴리오로 정리
[할 일] 저장소 루트에 README.md 를 만들어줘:
 1. 한 줄 소개: 이 저장소는 GPT-2급 LLM을 밑바닥부터 구현·훈련·튜닝한
    한 학기의 기록이다 (모든 코드는 코딩 에이전트 지휘로 작성)
 2. 주차별 산출물 지도: weekNN | 주제 | 핵심 파일 | 대표 결과 한 줄
    (각 주차 report.md 에서 발췌)
 3. 재사용 자산 목록: 성질 테스트 4종, 품질 게이트 3종, 검증 패턴,
    정답지 수치 — 각각 파일 경로와 함께
 4. 하이라이트: 10주차 4모델 비교표와 프로젝트 결과 요약
 5. 재현 방법: 환경(컨테이너), 주차별 실행 진입점
[제약] 없는 것을 포장하지 말 것 — 링크가 실재하는지 전부 확인 후 작성
[검증] README의 모든 상대 링크가 유효한지 검사해 보고할 것
```

이 저장소는 과제 제출물이 아니라 **"에이전트 시대에 일하는 법을 아는 사람"의 증거물**이다. 커밋 이력에는 여러분의 지시가, 테스트에는 여러분의 검증이, report에는 여러분의 해석이 남아 있다. 그것이 이 수업이 가르치려던 전부다 — 모델의 구조, 그리고 명세하고 검증하고 해석하는 사람의 역할.

한 학기 수고했다. 이제 여러분의 장비에는 여러분이 키운 모델이 있다.
