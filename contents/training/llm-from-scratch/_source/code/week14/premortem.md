# P14-1 사전 부검(pre-mortem) — 팀 «캐시왕» 제안서

역할: 회의적인 심사위원 · 제약: 대안 주제를 제안하지 않는다. 이 주제 안에서만 비판한다.

## 1. "금요일에 실패했다" — 가장 그럴듯한 원인 5개

### 원인 1 (기술) — 캐시를 쓸 때 위치 임베딩 인덱스가 0부터 다시 시작한다

캐시 없는 forward 는 매번 시퀀스 전체를 넣으므로 `pos_emb(arange(seq_len))` 이
자연히 맞는다. 캐시를 쓰면 새 토큰 1개만 넣게 되는데, 이때도 `arange(1)` 을 쓰면
**모든 새 토큰이 위치 0** 으로 들어간다. 로짓이 미묘하게 달라져 20~30 토큰쯤에서
출력이 갈라진다. 짧은 생성으로만 확인하면 통과한 것처럼 보인다 —
제안서의 "최소" 마일스톤이 32토큰이라 여기서 걸러지지 않을 가능성이 크다.

### 원인 2 (기술) — 코잘 마스크를 새 토큰 1개 기준으로 잘라내지 못한다

5주차 `CausalAttention` 은 `mask[:num_tokens, :num_tokens]` 로 정사각 마스크를
쓴다. 캐시 모드에서 query 는 1개, key 는 t 개이므로 마스크가 **1×t** 여야 하는데
정사각 슬라이싱을 그대로 두면 shape 오류가 나거나(운이 좋은 경우),
브로드캐스팅이 되어 조용히 잘못된 값을 낸다(운이 나쁜 경우).
후자면 출력이 달라지는데 원인 1과 증상이 구분되지 않아 디버깅이 길어진다.

### 원인 3 (기술/설계) — 컨텍스트 초과 시 캐시만 남고 입력만 잘린다

제안서 성공 기준 3번이 바로 이 지점인데, 마일스톤에서는 "도전"도 아니고
아예 빠져 있다. 크롭이 발생하면 입력 시퀀스는 앞이 잘리지만 캐시는 그대로 남아
**캐시 길이와 위치 인덱스가 어긋난다.** 512토큰 벤치마크(기대 마일스톤)에서는
ctx 1024 를 넘지 않아 드러나지 않고, 시연 때 긴 대화에서 터진다.

### 원인 4 (일정) — 벤치마크가 목요일 밤으로 밀린다

구현(김세연)이 끝나야 벤치마크(박도윤)가 시작되는 직렬 구조다.
동일성 게이트가 수요일에 깨지면 목요일 내내 디버깅이고, tokens/sec 곡선은
금요일 새벽에 한 번 돌린 값이 된다. 9주차에서 배운 워밍업·`synchronize` 규약을
지킬 시간이 없어 **측정 편차가 이득보다 커진다.** 1.5배를 넘겼는지조차 말할 수 없게 된다.

### 원인 5 (협업) — 두 사람이 같은 "출력이 같다"를 다른 뜻으로 쓴다

구현 리드는 "생성 문장이 같다", 검증 리드는 "토큰 ID 텐서가 `torch.equal`" 을
뜻하는데 합의 없이 진행한다. 디코딩된 문자열은 같은데 토큰 ID 가 다른 경우가
실제로 존재한다(같은 문자열로 디코딩되는 다른 토큰 조합). 금요일에
"통과했다/아니다"로 팀 안에서 결론이 갈린다. 14.7 절이 경고한
**"거의 같음으로 넘어가려는 시도"** 가 악의 없이 발생하는 경로다.

## 2. 원인별 — 화요일 조기 신호 1개 / 예방 조치 1개

| # | 화요일에 감지할 수 있는 조기 신호 | 예방 조치 |
|---|---|---|
| 1 | 캐시 모드로 **1토큰만** 생성했을 때의 로짓 벡터가 무캐시와 `allclose` 하지 않다. 문장을 볼 필요도 없다 | 생성 루프를 만들기 **전에** "프리필 t토큰 → 1토큰 디코드" 단계에서 로짓을 대조하는 스크립트부터 작성한다. 위치 인덱스를 `cache_len` 오프셋으로 넘기는 시그니처를 그때 확정한다 |
| 2 | 캐시 모드 forward 에서 `attn_scores.shape` 를 찍었을 때 `[B, H, 1, t]` 가 아니다 | 마스크 슬라이싱을 `mask[cache_len:cache_len+q_len, :k_len]` 로 일반화하고, q_len=1 과 q_len=t 두 경우를 모두 도는 shape 단위 테스트를 화요일에 추가한다 |
| 3 | `len(cache)` 와 `pos` 오프셋을 함께 출력해 보면 ctx 를 넘긴 순간 두 값이 어긋난다 | 7주차 크롭 테스트를 **화요일에 먼저 이식**해 실패하는 테스트를 확보한다(제안서 리스크 2의 플랜 B 를 플랜 A 로 앞당긴다). ctx 를 1024 대신 **64로 낮춘 소형 설정**으로 초과 상황을 강제로 만든다 |
| 4 | 화요일 스탠드업에서 박도윤이 "구현 대기 중"이라고 말한다 | 벤치마크 하네스를 **무캐시 모델만으로 먼저** 완성한다. 캐시 구현은 나중에 끼워 넣기만 하면 되도록 인터페이스(`generate(model, ..., use_cache: bool)`)를 화요일에 합의한다 |
| 5 | 두 사람이 각자 쓴 "동일성" 문장을 나란히 놓았을 때 판정 방법이 서로 다르다 | 화요일에 **테스트 코드로 정의를 고정한다**: `assert torch.equal(ids_cached, ids_plain)`. 문서가 아니라 실행되는 코드가 정의다. 이 테스트를 저장소에 먼저 커밋한다 |

## 3. 성공 기준(2번 항목) 비판 — 검증 가능하게 쓰였는가

**기준 1 — "1토큰도 다르지 않을 것 (256토큰 × 10개 프롬프트)"**
가장 잘 쓰였다. 대상(토큰), 규모(256×10), 임계(0건)가 다 있다.
다만 **비교 단위가 명시되지 않았다.** 토큰 ID 텐서인지 디코딩된 문자열인지 적어라
(원인 5 가 이 구멍에서 나온다). 그리고 10개 프롬프트를 **누가 어떻게 고르는지**가 없다.
짧고 쉬운 프롬프트 10개면 통과가 쉬워진다 — 프롬프트 목록을 제안서에 고정하거나,
"12주차 test 분할의 앞 10개" 처럼 재현 가능한 규칙으로 못 박아라.

**기준 2 — "256토큰 생성에서 tokens/sec 1.5배 이상"**
**측정 방법이 통째로 빠졌다.** 이대로면 검증 불가다. 최소한 다음이 필요하다.
- 무엇 대비 1.5배인가 — 같은 모델·같은 프롬프트의 무캐시 생성 대비임을 명시
- 몇 회 측정해 어떻게 집계하는가 — 9주차 규약(워밍업 1회 후 3회 측정, 중앙값)
- `torch.cuda.synchronize()` 를 시작·종료에 넣는가 — 안 넣으면 측정값이 의미 없다
- tokens/sec 의 분모가 생성 토큰 수인가 프리필 포함인가 — 프리필을 포함하면
  캐시의 이득이 희석되어 1.5배를 못 넘길 수 있다. 정의를 먼저 정하라
- 1.5배가 **어느 길이에서**인가 — 256 이라 썼지만 마일스톤은 {32,128,256,512} 곡선이다.
  32토큰에서는 1.5배가 안 나올 가능성이 높다. "256 이상에서" 로 한정하라

**기준 3 — "컨텍스트 1024 초과 시 크롭이 동작하고 캐시가 함께 잘릴 것"**
**측정 방법도 임계값도 없다.** "동작한다"는 판정 불가능한 서술이다.
검증 가능하게 바꾸면: "ctx=64 로 낮춘 소형 모델에서 128토큰을 생성했을 때
(a) 예외가 나지 않고 (b) 캐시 길이가 항상 64 이하이며 (c) 무캐시 크롭 생성과
출력이 완전히 같다 — pytest 로 확인". 그리고 이 기준은 **마일스톤에 없다.**
성공 기준에는 있고 마일스톤에는 없으면 금요일에 아무도 하지 않은 항목이 된다.
최소/기대/도전 중 어디에 넣을지 정하라.

**공통 지적 — "실패도 성공 기준"이 없다.**
동일성 게이트가 끝내 안 맞으면 이 프로젝트는 0점인가? 14.6 루브릭은
"검증과 실패 분석 30점, 실패 자체는 감점이 아니다" 라고 한다.
성공 기준에 "게이트 불통과 시, 갈라지는 첫 토큰 위치와 그때의 로짓 차이를
층별로 특정한다" 를 한 줄 넣어 두면 최악의 경우에도 30점 항목이 살아난다.
