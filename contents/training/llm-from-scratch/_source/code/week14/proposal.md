# 팀명 / 트랙 / 팀원(역할)

**팀명**: 캐시왕 · **트랙**: A (아키텍처 — KV 캐시)
**팀원**: 김세연(지시·구현 리드) / 박도윤(검증·벤치마크 리드)

## 1. 목표 (2~3문장)

7주차 `generate_text_simple` 은 매 토큰마다 전체 시퀀스를 다시 forward 한다.
이미 계산해 둔 과거 토큰의 K·V 를 캐시에 보관해 재계산을 없애고,
생성 길이가 길어질수록 이득이 커지는지를 실측한다.
출력은 캐시 유무와 무관하게 완전히 같아야 한다.

## 2. 성공 기준 (정량)

- 캐시 on/off 의 greedy 출력이 **1토큰도 다르지 않을 것** (256토큰 생성 × 10개 프롬프트)
- 256토큰 생성에서 tokens/sec **1.5배 이상**
- 컨텍스트 1024 초과 시 크롭이 동작하고 캐시가 함께 잘릴 것

## 3. 마일스톤: 최소 / 기대 / 도전

- **최소**: KV 캐시 동작 구현, 32토큰 생성에서 출력 동일
- **기대**: 동일성 게이트 통과 + 생성 길이 {32, 128, 256, 512} 별 tokens/sec 곡선
- **도전**: GQA 를 추가 구현해 캐시 메모리 사용량 비교

## 4. 역할 분담

- 김세연: KV 캐시 자료구조 설계·구현 지시, 크롭 정책 결정
- 박도윤: 동일성 게이트 테스트 작성, 벤치마크 스크립트, 메모리 측정

## 5. 리스크 상위 3개와 플랜 B

1. 캐시와 위치 임베딩의 인덱스가 어긋나 출력이 미세하게 달라진다
   → 플랜 B: 1토큰 생성부터 단계별로 캐시/무캐시 로짓을 대조
2. 컨텍스트 초과 시 캐시 잘라내기를 빠뜨린다
   → 플랜 B: 7주차 크롭 테스트를 먼저 이식해 실패하는 테스트부터 확보
3. 두 사람의 작업이 같은 파일에서 충돌한다
   → 플랜 B: 구현/테스트 파일을 분리하고 브랜치 분업
